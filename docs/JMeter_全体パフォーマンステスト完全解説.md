# JMeterを用いた全体パフォーマンステスト完全解説

**文書種別:** 実務向け解説（用語・観点・レポート・実行注意点・AWS構成別の測り方）  
**対象読者:** 性能試験を初めて設計する人、インフラとアプリの境目で結果が読めない人、小学生にも説明できる言葉で原理を押さえたい人  
**対象ツール:** Apache JMeter 5.6.3（2026年時点の公式最新安定版。Java 8以上必須、実行は Java 17 以上を推奨。次期メジャーは Java 17 必須予定）  
**対象構成の典型例:**

```text
クライアント
  → Amazon API Gateway（REST / HTTP API、認可、スロットル）
    → Application Load Balancer（ALB）
      → Amazon ECS（Fargate / EC2、タスク単位）
        → Amazon ElastiCache（Valkey / Redis OSS / Memcached）
        → Amazon RDS Proxy
          → Amazon Aurora Serverless v2
        → 帳票サーバ（SVF / JasperReports 等への同期・非同期呼び出し）
```

**この文書が答える問い:**

1. 全体パフォーマンステストで、何を・なぜ・どの順番で見るのか。
2. JMeter の用語は、内部で何が起きているのか。
3. どのレポートを残し、何をもって合格とするのか。
4. 実行時に結果を壊す落とし穴は何か。
5. API Gateway があるとき、なぜ ALB より後ろから打つべきなのか。
6. ECS はなぜサービス平均ではなくタスク単位で取るのか。
7. Aurora Serverless v2、RDS Proxy、ElastiCache、帳票サーバを挟むと、何が「アプリの遅さ」に見えるのか。

**情報の時点:** 2026-09。数値・上限・機能名は AWS 公式ドキュメントおよび Apache JMeter 公式マニュアルに基づく。クォータはリージョン・アカウントで増減するため、試験前に自アカウントの Service Quotas を確認すること。

## 0. 最初に覚える一枚絵（小学生向け）

学校の給食を想像する。

- **お客（仮想ユーザ）** がたくさん来る。JMeter は「お客役をたくさん作る機械」。
- **受付（API Gateway）** は「1秒に何人まで通してよいか」を決める門。門が狭いと、厨房が速くても行列になる。
- **配膳口（ALB）** は、来た人を空いている窓口に振り分ける。
- **調理員ひとり（ECS タスク）** が実際に料理を作る。調理員を何人にするか、ひとりが何皿作れるかが本番の能力。
- **冷蔵庫（ElastiCache）** は、よく出すおかずをすぐ取れる棚。棚に無いと、奥の倉庫まで取りに行く。
- **倉庫の受付（RDS Proxy）** は、倉庫に入れる人数を整理する。整理が壊れると、倉庫の席がすぐ埋まる。
- **倉庫（Aurora）** が本当の材料置き場。棚の広さ（ACU）が自動で伸び縮みする。
- **印刷室（帳票サーバ）** は、成績表を一枚ずつ丁寧に印刷する部屋。同時に何台まで刷れるかが決まっている。

**いちばん大事な約束:**

> 厨房の速さを知りたいのに、校門の幅だけを測ってはいけない。  
> 測りたい部屋の直前からお客を入れる。

API Gateway の性能試験をしたつもりが、実は API Gateway の 10,000 RPS 制限に当たっていた、というのはこの約束を破ったときに起きる。

## 1. パフォーマンステストが必要になった歴史

### 1.1 コンピュータが「ひとり用」だった時代

初期のコンピュータは、順番待ちの計算機だった。人が並んでパンチカードを渡し、結果を待つ。遅さは「計算そのものの遅さ」で、同時に何千人も叩く、という問題はまだ小さかった。

### 1.2 オンラインが始まった（1960〜1980年代）

銀行の窓口端末、航空座席予約（SABRE など）が「同時に大勢が同じ計算機を使う」世界を作った。ここで初めて、

- 同時接続数
- 応答時間
- ピーク時に落ちないこと

が商売の生死になった。TPC（Transaction Processing Performance Council）のような業界ベンチマークが生まれたのは、「速さの自慢を公平に比べたい」という需要からである。

### 1.3 Web が爆発した（1990年代）

ブラウザが世界中から同じ URL を叩くようになった。有名サイトに記事が載るとアクセスが何倍にも跳ねる（いわゆる Slashdot 効果）。サーバは「昨日まで静か、今日は壊滅」になった。

この時代に負荷試験ツールが一般化した。JMeter の原型もこの流れにある。

### 1.4 SOA・API・クラウド（2000〜2010年代）

システムが「大きな一つ」から「小さなサービスの集まり」になった。遅さの原因が、自前のアプリとは限らなくなった。

- 前段の API 管理
- ロードバランサ
- コンテナの本数
- コネクションプール
- キャッシュの当たり外れ
- データベースの自動スケール
- 帳票やバッチのような重い脇役

「全体が遅いか」と「どこが遅いか」を分けて測らないと、改善しても効かない。

### 1.5 サーバレスと従量課金（2010年代後半〜2020年代）

API Gateway、Fargate、Aurora Serverless、ElastiCache Serverless は「使った分だけ」に近づいた。同時に、

- アカウント全体の上限
- バースト（短時間の突発）
- スケールが追いつくまでの空白
- コールドスタートやバッファプールの冷え

が、アプリのバグと同じ見た目の「遅さ」を作るようになった。

**だから今、全体パフォーマンステストは「アプリを殴る」作業ではない。構成のどの段が先に音を上げるかを、意図して切り分ける作業である。**

## 2. パフォーマンステストの種類（何を証明したいか）

種類を混ぜると、報告書が読めなくなる。先に「今日の試験はどれか」を一文で書く。

| 種類 | 小学生向け | 何を証明するか | 典型的な失敗 |
| --- | --- | --- | --- |
| スモーク性能 | 火が付くか見る | スクリプトと観測が動く | 本試験の数字として使う |
| 負荷試験（Load） | 平常の給食時間 | 目標負荷で SLA を満たす | ランプが短すぎてスケールが間に合わない |
| ストレステスト | 限界まで人を増やす | 壊れ方と回復 | データ破壊を許容設計していない |
| スパイク | 突然どっと来る | バースト耐性 | API Gateway バーストや ALB スケールに当たる |
| ソーク／耐久 | 何時間も出し続ける | メモリリーク、接続リーク、GC、ディスク | 短時間の平均値だけで合格にする |
| キャパシティ | 何人までなら安全か | 増設の単位（タスク何個か） | サービス平均だけで外挿する |
| フェイルオーバー | 壊したときの速さ | 切替時間とエラー率 | 試験中にフェイルオーバーが起きて数字が汚染される |

**全体パフォーマンステスト** は、上の「負荷試験」を中心に、必要ならスパイクとソークを足す。目的は「本番相当の業務ミックスで、目標ピークを安定して処理できること」である。コンポーネント単体のマイクロベンチは別試験として残す。

## 3. Apache JMeter とは何か

### 3.1 登場の歴史

1998 年、Apache JServ（Java 製 Web サーバ）の開発者 Stefano Mazzocchi が、自分たちのサーバの動きを測るために作り始めた。当時は「Java のサーバを、Java で負荷をかける」ための内製道具に近かった。

2001 年に Apache Jakarta のサブプロジェクトになり、GUI でシナリオを組める負荷ツールとして広がった。2011 年に Apache のトップレベルプロジェクトになった。名前の JMeter は「Java で測るメーター」という意味合いで、電気の電流計（ammeter）をもじっている。

**なぜ残ったか:**

- プロトコルが HTTP 以外にも広がった（JDBC、JMS、FTP、gRPC プラグインなど）。
- テスト計画が XML（`.jmx`）で保存でき、CI に載せやすい。
- 企業が一度作った資産を捨てにくい。
- 2026 年時点でも、既存 JMX 資産がある現場では主流の一つ。新規は k6 や Gatling を選ぶチームも増えているが、本文書は JMeter を軸にする。

### 3.2 動作原理（中のイメージ）

JMeter はブラウザではない。ブラウザの見た目は描かない。代わりに、

1. **スレッド**（仮想ユーザの体）を N 本作る。
2. 各スレッドが **サンプラー** で「リクエストを出す」。
3. 応答が返るまで待つ（待ち時間も測る）。
4. アサーションで「成功か失敗か」を判定する。
5. 結果を **SampleResult** として記録する。
6. リスナーや HTML レポートが集計する。

タイムラインはだいたいこうなる。

```text
スレッド開始
  →（ランプアップ待ち）
  → ループ開始
      → タイマー（思考時間）
      → サンプラー送信
      → Connect Time（TCP/TLS の握手）
      → Latency（最初のバイトが来るまで）
      → Elapsed（最後のバイトまで）
      → アサーション
      → 後処理（JSON 抽出、Cookie 更新）
  → ループ終了
スレッド終了
```

**小学生向け:** JMeter は「同じ注文を、たくさんの人が同時に出す機械」である。ストップウォッチは「注文してから料理が全部届くまで」を測る。

### 3.3 GUI と非 GUI

| モード | 用途 | 本番負荷で使うか |
| --- | --- | --- |
| GUI | シナリオ作成、デバッグ、結果の目視 | **使わない** |
| CLI（非 GUI、`-n`） | 本試験 | **必ずこれ** |

公式ベストプラクティスは明確である。GUI は描画とリスナーで CPU・メモリを食う。測っているつもりが、測る機械自身が詰まっている、という事故が起きる。

本試験の標準コマンド:

```bash
jmeter -n -t test.jmx -l results.jtl -e -o html-report -j jmeter.log
```

| 引数 | 意味 |
| --- | --- |
| `-n` | 非 GUI |
| `-t` | テスト計画（`.jmx`） |
| `-l` | 生結果（`.jtl`。実体は CSV 推奨） |
| `-e -o` | 終了後に HTML ダッシュボードを出す |
| `-j` | JMeter 自身のログ |
| `-Jkey=value` | スレッド数などを実行時に差し込む |
| `-q extra.properties` | 追加プロパティファイル |
| `-Gkey=value` | 分散試験で全サーバに渡すプロパティ |

### 3.4 最新版で押さえること（5.6.3）

- 実行は Java 8 以上、推奨 Java 17 以上。
- 公式は「最新版を使え。3 世代以上古い版は避ける」。
- BeanShell は負荷試験向けではない。JSR223 + Groovy（コンパイルキャッシュあり）を使う。
- `user.properties` を変更し、`jmeter.properties` 本体は触らない（次バージョンへの移行が楽）。
- HTML ダッシュボードは JMeter 3.0（2016）以降の標準成果物。

## 4. JMeter 用語辞典（動作原理つき）

用語は「名前 → 小学生向け → 中で起きていること → 試験での使い方」の順で読む。

### 4.1 テスト計画（Test Plan）

試験の設計図全体。スレッドグループ、設定、サンプラー、リスナーが入る入れ物。ファイルは `.jmx`（XML）。

**注意:** 機能テストモード（Functional Mode）をオンにすると応答本文を全部保持し、負荷試験ではメモリが死ぬ。本試験ではオフ。

### 4.2 スレッドグループ（Thread Group）

仮想ユーザの集団。設定は次の三つが核。

| 項目 | 意味 |
| --- | --- |
| Number of Threads | 同時に動く仮想ユーザ数 |
| Ramp-up | その人数に達するまでの秒数 |
| Loop Count / Duration | 何回繰り返すか、何秒続けるか |

**動作イメージ:** 100 スレッド、ランプ 100 秒なら、だいたい 1 秒に 1 人ずつ厨房に入る。ランプ 1 秒なら、ほぼ同時に 100 人が押し寄せる（スパイク）。

**Open Model Thread Group（5.5 以降）:** 「同時ユーザ数」ではなく「到着率（1秒に何人来るか）」で負荷を描ける。現代の Web は「同時接続」より「到着率」の方が現実に近いことが多い。

**setUp / tearDown Thread Group:** 本負荷の前にログイン用トークンを取る、後でデータを掃除する、などの準備・後始末専用。本負荷の TPS に混ぜない。

### 4.3 仮想ユーザ（VU）とスレッド

JMeter の 1 スレッド ≒ 1 仮想ユーザ。本物の人間と違う点:

- 思考時間を入れないと、人間よりはるかに高頻度で叩く。
- ブラウザの並列ダウンロード（CSS/JS/画像）を再現するには「埋め込みリソース取得」や別サンプラーが要る。
- HTTP/1.1 のコネクション再利用、Keep-Alive、HTTP/2 の設定で「見た目の同時ユーザ」と「サーバ側コネクション数」がずれる。

**Coordinated Omission（協調的欠測）:** サーバが遅くなると、スレッドが応答待ちで次のリクエストを出せない。すると「遅いはずの時間帯のサンプルが減り、平均が良く見える」。これはツールのバグというより、クローズドワークロード（スレッド数が固定）の性質である。対策は、到着率ベースのモデル、十分なスレッド、タイムアウトの明示、パーセンタイルの採用。

### 4.4 サンプラー（Sampler）

実際に仕事をする部品。HTTP Request が最も多い。他に JDBC、JMS、TCP、gRPC（プラグイン）、JSR223 など。

HTTP Request の内部時計:

| 指標 | 何を測るか | たとえ |
| --- | --- | --- |
| Connect Time | TCP と TLS の握手 | 電話をかけるまでの時間 |
| Latency | リクエスト送信後、最初の応答バイトまで | 相手が「はい」と声を出すまで |
| Elapsed（Response Time） | 最初から最後のバイトまで | 話が全部終わるまで |
| Idle Time | サンプラー前後の待ち（タイマー等） | 注文前にメニューを見ている時間 |

**TTFB（Time To First Byte）** は Latency に近い。本文が大きい PDF では Latency は短く Elapsed だけ長い、が典型。帳票はまさにこれ。

### 4.5 トランザクションコントローラ（Transaction Controller）

ログイン〜検索〜登録のように、複数サンプラーを「業務 1 件」に束ねる。

- **Generate parent sample:** 親だけをレポートに出すか、子も出すか。
- **Include duration of timer and pre-processors:** 思考時間を業務時間に含めるか。SLA が「画面操作込み」なら含め、API 単体なら含めない。混ぜると比較不能になる。

HTML レポートの「Transactions per second」は、このコントローラの親サンプルを含む。Hits per second は含まない。**TPS とヒット/秒は別物**である。

### 4.6 コントローラ全般

| 名前 | 役割 |
| --- | --- |
| Simple Controller | ただのフォルダ |
| Loop Controller | 指定回数繰り返す |
| Once Only Controller | スレッドあたり一度（ログイン向き） |
| If Controller | 条件分岐 |
| Throughput Controller | 割合で実行（例: 検索 80%、登録 20%） |
| Critical Section Controller | 同時に一人だけ通す（データ競合防止。負荷を歪めるので常用しない） |
| Include Controller | 別 JMX を取り込む（実行時に展開され、リソース削減にはならない） |
| Module Controller | 同じ断片を再利用 |

### 4.7 タイマー（Timer）

人間の「考える時間」。入れないとロボット攻撃になる。

| 名前 | 性質 |
| --- | --- |
| Constant Timer | 固定待ち |
| Uniform Random Timer | 範囲のランダム |
| Gaussian Random Timer | 正規分布 |
| Poisson Random Timer | 到着の揺らぎ |
| Constant Throughput Timer | 目標 TPS に合わせて待つ |
| Precise Throughput Timer | より正確な TPS 制御 |
| Synchronizing Timer | 全員で待ち合わせして同時発射（スパイク再現。常用禁止） |

**置き場所:** タイマーは同じスコープのサンプラーの**前**に効く。意図しないサンプラーまで遅くしていないか、ツリーの入れ子を毎回確認する。

### 4.8 設定要素（Config Element）

| 名前 | 役割 |
| --- | --- |
| HTTP Request Defaults | ホスト、プロトコル、Keep-Alive の共通値 |
| HTTP Header Manager | Authorization、Content-Type など |
| HTTP Cookie Manager | Cookie をスレッドごとに保持。本番相当にするなら必須級 |
| HTTP Cache Manager | ブラウザキャッシュ相当。静的資源を何度も取らない |
| CSV Data Set Config | ユーザ ID や伝票番号をファイルから読む。スレッドごとに Recycle / Stop を選ぶ |
| DNS Cache Manager | 仮想ユーザごとに DNS を解決。JVM の DNS キャッシュ固定を避ける |
| Counter / Random Variable | 一意キー生成 |
| User Defined Variables | 定数。実行時上書きは `__P()` と `-J` が本命 |
| JDBC Connection Configuration | DB 直叩き試験用。全体試験でアプリをバイパスする目的以外では慎重に |

### 4.9 前置・後置処理（Pre/Post Processors）

| 名前 | 役割 |
| --- | --- |
| JSR223 PreProcessor | 送信前にペイロードを組む |
| Regular Expression Extractor | 旧来の相関（トークン抜き） |
| JSON Extractor | REST の ID 抜き |
| Boundary Extractor | 開始・終了文字列で抜く |
| JSR223 PostProcessor | 複雑な相関、加工 |
| JSR223 Assertion | 本文の意味チェック |

**相関（Correlation）:** ログインの CSRF、セッション ID、業務 ID を次のリクエストに引き継ぐこと。これが壊れると、負荷試験なのに 401/403 の山になる。歴史的には、録画したスクリプトが「録画した人のセッション」のまま再生される事故が多発し、抽出子が必須になった。

### 4.10 アサーション（Assertion）

HTTP 200 だけでは成功ではない。在庫なしでも 200 で JSON エラー、は現場でよくある。

- Response Assertion（文字列、コード）
- JSON Assertion
- Duration Assertion（遅すぎたら失敗）
- Size Assertion

**本試験ではアサーションを最小限にする。** 重い正規表現アサーションは JMeter 側 CPU を食う。合格判定の本命は、サーバ側の業務ログと HTTP コード、必要なら軽い JSON キーチェック。

### 4.11 リスナー（Listener）

結果の見せ方。**本試験中はほぼ全部オフ。** 公式も View Results Tree / Table はデバッグ専用と明記している。

本試験で残すもの:

- コマンドラインの `-l`（Simple Data Writer 相当）
- 必要なら Backend Listener（InfluxDB 2 / Graphite）でリアルタイム

GUI の Aggregate Report は事後に JTL を読み込んで見る。実行中に付けない。

### 4.12 ロジックと関数

よく使う関数:

| 関数 | 用途 |
| --- | --- |
| `${__P(threads,10)}` | プロパティ。CLI から `-Jthreads=50` |
| `${__time()}` | タイムスタンプ |
| `${__UUID()}` | 一意 ID |
| `${__threadNum}` | スレッド番号 |
| `${__V()}` | 変数名の間接参照 |
| `${__groovy()}` | 短い計算。負荷パスでは乱用しない |

スレッド間で変数は共有されない（設計）。共有が必要ならプロパティ、ファイル、外部ストア。安易な共有はロック待ちを生み、JMeter 自身がボトルネックになる。

### 4.13 分散試験（Distributed Testing）

1 台の JMeter が出せる同時スレッドには上限がある（CPU、帯域、ファイルディスクリプタ、GC）。超えるときは:

- 複数マシンで同じ JMX を独立実行し、後で JTL を結合する
- または Master/Worker の分散モード

分散モードはファイアウォール、時計同期（NTP）、結果の集約負荷に注意。近年は「独立実行 + 後結合」の方が単純で事故が少ない、という運用も多い。

### 4.14 JTL

生のサンプルログ。拡張子は歴史的に JTL（JMeter Test Log）だが、中身は CSV 推奨。XML は重い。

典型列:

`timeStamp,elapsed,label,responseCode,responseMessage,threadName,dataType,success,failureMessage,bytes,sentBytes,grpThreads,allThreads,URL,Latency,IdleTime,Connect`

これがすべてのレポートの原料である。失ったら再現できない。保管期限とマスキング（トークン、個人情報）を先に決める。

### 4.15 HTML ダッシュボードの指標

| 画面 | 見るもの |
| --- | --- |
| APDEX | 満足・許容・不満の比率。閾値は SLA に合わせて変更（既定 0.5 秒 / 1.5 秒は現代 API には不適切なことが多い） |
| Requests Summary | 成功/失敗の円グラフ |
| Statistics | 平均、最小、最大、90/95/99 パーセンタイル、スループット、受信 KB/s、エラー率 |
| Errors | コードとメッセージの内訳 |
| Over Time | 応答時間、スレッド数、TPS の時系列 |
| Throughput | Hits/s、Codes/s、Transactions/s |
| Response times vs Threads | スケール特性 |
| Latency vs Request | 飽和の兆候 |

**平均よりパーセンタイル。** 平均は少数の超遅延に引っ張られるか、逆に隠す。SLA は p95 か p99 で書く。

### 4.16 その他の重要語

| 用語 | 意味 |
| --- | --- |
| Throughput | 単位時間あたりの処理量。JMeter では主に件数/秒 |
| Bandwidth | バイト/秒。スループットとは別 |
| Error rate | 失敗サンプルの割合。定義（アサーション含むか）を報告書に書く |
| Think time | 操作と操作の間 |
| Pacing | 1 業務の開始間隔。Think time と別管理することがある |
| Warm-up | キャッシュ、JIT、接続プール、ALB、Aurora を温める時間。この区間は統計から除外する |
| Steady state | ランプ完了後の定常。合格判定の主戦場 |
| Saturation | 負荷を足しても TPS が増えず、遅延だけ増える点 |
| Bottleneck | いちばん細い管 |
| SLA / SLO / SLI | 約束 / 内部目標 / 測るもの |
| NFR | 非機能要件。性能要件の置き場所 |
| Workload mix | 検索 70%、更新 20%、帳票 10% のような比率 |
| Idempotency | 同じ更新を二度送っても壊れないこと。再試行試験に必要 |
| Backpressure | 下流が詰まっている合図を上流が知ること |

## 5. 全体パフォーマンステストで必要な観点

観点は「測る軸」である。軸が無い試験は、数字の山になる。

### 5.1 目的の観点（何のための試験か）

1. **リリース判定:** 今の構成で目標ピークを満たすか。
2. **サイジング:** ECS タスクは何個か、ACU の上限は幾らか、キャッシュノードは足りるか。
3. **ボトルネック発見:** 最初に折れる段はどこか。
4. **回帰:** 前回リリースより遅くなっていないか。
5. **コスト:** サーバレス課金がピークで幾らになるか（性能と同時に見る）。

目的が 1 と 3 では、打ち込み位置も成功条件も変わる。

### 5.2 業務の観点

- 本番のピークは「同時ユーザ」か「件/秒」か。両方あるなら両方書く。
- 重い画面（帳票、検索、一括更新）の比率。
- ログイン済みトラフィックと、認可なしヘルスチェックは別。
- データ量（テナント数、履歴年数、商品数）が試験データと本番で桁違いだと、DB だけ遅くなる。
- バッチや帳票の夜間処理とオンラインが重なるか。

**小学生向け:** 運動会の徒競走で timetrial するなら、本番と同じ靴、同じ距離、同じ人数で走る。スリッパで 50 m だけ走って「運動会は大丈夫」とは言わない。

### 5.3 プロトコルとクライアントの観点

- HTTP/1.1 か HTTP/2 か。ALB と API Gateway で扱えるものが違う。
- TLS の終端はどこか（CloudFront / API Gateway / ALB）。握手は Connect Time に出る。
- ペイロードサイズ。JSON 2 KB と PDF 5 MB ではボトルネックが CPU から帯域・メモリに移る。
- 認証（Cognito JWT、IAM SigV4、API キー）。トークン期限切れで試験後半だけ 401 になる事故が定番。
- Keep-Alive。毎回新規接続にすると、TLS で JMeter もサーバも死ぬ。

### 5.4 アーキテクチャの観点（最重要）

**段ごとに試験目的を分ける。**

| 段 | 何の試験になるか | 全体試験での扱い |
| --- | --- | --- |
| インターネット経路・WAF・CloudFront | CDN/WAF 試験 | アプリ試験からは外すか、別ラン |
| API Gateway | ゲートウェイのスロットル・認可・マッピング | **アプリ能力の主測定には使わない** |
| ALB | 振り分け、ヘルス、接続 | アプリ試験の標準エントリ |
| ECS タスク | アプリ本体 | **1 タスク能力を先に取る** |
| ElastiCache | ヒット率とホットキー | ウォームアップ必須 |
| RDS Proxy | 多重化とピン留め | ピン留め率を必ず見る |
| Aurora Serverless v2 | ストレージと計算の伸縮 | 最低 ACU を試験用に固定してから測る |
| 帳票サーバ | レンダリング並列 | 同期呼び出しなら全体の天井になりやすい |

詳細は第 8 章以降。

### 5.5 観測の観点（JMeter だけでは不合格）

JMeter が見るのは「外から測った時間と成否」だけである。中で何が待っていたかは、各段のメトリクスが要る。

最低限同時に取るもの:

- JMeter: 時系列の TPS、p95、エラー、アクティブスレッド、Connect/Latency
- API Gateway: Count、Latency、IntegrationLatency、4XX/5XX、429
- ALB: RequestCount、TargetResponseTime、HTTPCode_ELB_5XX、UnHealthyHostCount、ActiveConnectionCount
- ECS: タスク CPU/メモリ、タスク数、ALB RequestCountPerTarget
- RDS Proxy: ClientConnections、DatabaseConnections、DatabaseConnectionsCurrentlySessionPinned
- Aurora: CPU、ACU、DatabaseConnections、CommitLatency、BufferCacheHitRatio、Deadlocks
- ElastiCache: EngineCPUUtilization、CacheHitRate、Evictions、CurrConnections
- 帳票: キュー長、実行中ジョブ、JVM ヒープ、GC、一時ディレクトリ

**時計を合わせる。** JMeter マシン、CloudWatch、アプリログのタイムゾーンと NTP がずれると、相関ができない。

### 5.6 データの観点

- 試験ユーザは使い回すか、使い切るか。
- ユニーク制約で後半だけ失敗しないか。
- キャッシュを温めるデータと、ミスを再現するデータは別セット。
- 個人情報はマスキング。本番コピーは法務・セキュリティの許可。
- 帳票はページ数・画像・フォントで CPU が激変する。代表帳票を何種類か混ぜる。

### 5.7 合否の観点（先に書く）

試験後に「遅かった気がする」は合否ではない。事前に数値で書く。

例:

- 業務トランザクション X の p95 ≤ 500 ms（ALB 起点、ウォームアップ除外）
- エラー率 < 0.1%（4xx のうち業務的に正常なものを除外する定義を明記）
- 目標 800 TPS を 30 分定常で維持
- ECS タスク CPU 平均 < 70%（1 タスク飽和試験では意図的に 100% 近くまで見る）
- RDS Proxy ピン留め < 合意した閾値
- Aurora ACU が上限に張り付かない
- 帳票同期パスは別 SLA（例: p95 ≤ 8 s）で、API Gateway 29 秒に届かないこと

### 5.8 安全性の観点

- 本番で打たない。打つなら読み取り専用かつレート制限と告知。
- 書き込み試験は専用データとロールバック手段。
- 課金爆発（API Gateway のリクエスト課金、Fargate、Aurora ACU、データ転送、CloudWatch カスタムメトリクス）。
- 隣接システム（メール、外部帳票 SaaS、決済）はスタブ化する。スタブが速すぎると本番より楽観的になるので、本番相当の遅延を入れる。

## 6. 必要なレポート

レポートは「残さないと試験していないのと同じ」成果物である。JMeter の HTML だけでは、AWS 構成の切り分けはできない。

### 6.1 必ず残す一次資料

| 成果物 | 中身 | なぜ必要か |
| --- | --- | --- |
| テスト計画書 | 目的、範囲、打ち込み位置、負荷モデル、データ、合否、リスク | 後から「何を測ったつもりか」が残る |
| `.jmx` と版 | 実行したシナリオ | 再現 |
| `user.properties` / `-J` 値 | スレッド、ホスト、期間 | 再現 |
| `.jtl` | 全サンプル | 再集計の唯一の原料 |
| `jmeter.log` | JMeter 側エラー | クライアントボトルネックの証拠 |
| HTML Dashboard | 関係者への概要 | 説明用。一次資料ではない |
| 実行コマンドと開始終了 UTC | いつ打ったか | CloudWatch と接合 |
| 負荷ジェネレータの CPU/メモリ/帯域 | クライアントが先に死んでいないか | 無効試験の検出 |
| CloudWatch ダッシュボード出力 | 各段の時系列 | ボトルネック位置 |
| アプリログ・トレースの抽出 | 遅延の内訳 | p99 の中身 |
| 合否レポート | 要件対実測 | リリース判断 |
| 既知問題と次アクション | 直す人・期限 | 試験を改善に変える |

### 6.2 JMeter HTML ダッシュボードの使い方

公式が出すグラフは次を含む（JMeter ユーザマニュアル "Generating Dashboard Report"）。

- APDEX 表
- 成功/失敗円グラフ
- Statistics（パーセンタイル含む）
- エラー表、サンプラー別 Top 5 エラー
- Response times Over Time
- Response times Percentiles Over Time
- Active Threads Over Time
- Bytes throughput Over Time
- Latencies Over Time
- Connect Time Over Time
- Hits Per Second
- Codes Per Second
- Transactions Per Second
- Response Time vs Request
- Latency vs Request
- Response time Overview / Percentiles / Distribution

**報告書に貼る最小セット:**

1. 負荷プロファイル（Active Threads Over Time）
2. 業務別 TPS（Transactions Per Second）
3. 業務別 p95/p99（Statistics + Percentiles Over Time）
4. エラー内訳
5. Connect Time（TLS と接続枯渇の兆候）

粒度（`jmeter.reportgenerator.overall_granularity`）は短時間試験なら 1000 ms、長時間なら 60000 ms。1 秒未満はスループットグラフが崩れる（公式注意）。

APDEX 閾値は必ず業務 SLA に合わせて変更する。既定の 500 ms / 1500 ms のまま出すと、帳票が全部「不満」になり議論が壊れる。

### 6.3 試験種別ごとの追加レポート

| 試験 | 追加で残すもの |
| --- | --- |
| 1 タスク飽和 | タスク CPU/メモリ、TPS 対 CPU、飽和点 |
| スケールアウト | タスク数増加と TPS の直線性、ALB の 5xx、スケール遅延 |
| スパイク | 429/503 の時刻、バースト、オートスケール開始時刻 |
| ソーク | ヒープ、GC、接続数の右肩上がり、エラーの時間ドリフト |
| 帳票混在 | 帳票キュー、同期待ち、API タイムアウト 504 |
| キャッシュコールド | ヒット率 0 近傍の p95 と、ウォーム後の p95 |
| Aurora スケール | ACU 時系列と p95 の lagged 相関 |

### 6.4 報告書の標準目次（関係者向け）

1. 結論（合格 / 条件付き合格 / 不合格）を 1 ページ
2. 測った範囲と、測っていない範囲（API Gateway を外した、など）
3. 負荷モデルとデータ
4. 結果サマリ表
5. ボトルネックと証拠（グラフ 2〜3 枚）
6. リスクと残件
7. 付録（生データ場所、再現手順）

結論を最後に回さない。忙しい人は 1 ページ目しか読まない。

### 6.5 数値の見せ方

- ウォームアップ除外を明記（例: 最初 10 分除外）。
- 平均だけでなく p50 / p95 / p99 / max。
- エラーは「率」と「件数」と「種類」。
- 比較は同じ打ち込み位置、同じデータサイズ、同じタスク数で。
- 「ネットワーク込み」と「TargetResponseTime（ALB→タスク）」を並べると、外の遅さか中の遅さか分かる。

## 7. 実行する際の注意点（結果を壊すもの）

### 7.1 JMeter 側が先に死ぬ

兆候:

- ジェネレータ CPU が 70〜80% 超
- GC が多い
- Connect Time が突然伸びる
- エラーは主にクライアントタイムアウト
- サーバ側 CPU はまだ低い

対策（公式ベストプラクティス）:

- 非 GUI
- リスナー削減、Tree 禁止
- CSV 結果、必要列だけ
- アサーション最小
- Groovy はコンパイルキャッシュ、`${var}` 埋め込み禁止（`vars.get` を使う）
- 同様サンプラーの複製よりループ + CSV
- 機能モード禁止
- ヒープは `HEAP` 環境変数で適切に（大きすぎると GC 停止が長い）
- 分散または複数ジェネレータ
- ジェネレータは対象と同じリージョンの別 AZ、または意図したインターネット経路。混在させない

**クライアント健全性の目安（負荷ツール一般）:** エンジン CPU/メモリは平均 70% 未満を目安にする、という運用が多い（BlazeMeter Engine Health 等でも同趣旨）。超えたら結果は疑う。

### 7.2 ランプアップ不足

オートスケール、ALB、Aurora ACU、キャッシュ、JIT、コネクションプールは、いきなりピークを出されると「本番では起きない壊れ方」をする。

- 全体試験の定常は、ランプ 5〜15 分以上を起点に考える（規模による）。
- スパイク試験は別ラン。混ぜない。
- ECS の新規タスク起動（イメージ pull、エージェント、ヘルスチェック）は数十秒〜数分。その間の 5xx は「アプリが遅い」ではない。

### 7.3 思考時間ゼロ

TPS が本番の何十倍にもなる。DB 接続、帳票並列、CPU が非現実的に壊れる。逆に、思考時間を入れすぎると負荷不足で「全部合格」になる。本番の操作ログから分布を作る。

### 7.4 データの偏り

- 同じ主キーばかり叩く → キャッシュが当たりすぎ、または行ロックで死ぬ。
- 毎回新規で巨大データを作る → ディスクとインデックスが試験専用の壊れ方をする。
- ログインユーザ 1 人を使い回す → セッションストアと認可キャッシュが甘くなる。

### 7.5 時刻・期間

- サマータイムや JST/UTC の取り違え。
- CloudWatch の標準解像度 60 秒。短い試験だと点が足りない。ECS は 2026 年に 20 秒解像度の高速オートスケール用メトリクスが追加されている。短いスパイクは高解像度かアプリメトリクスで見る。
- 試験終了直後にスケールインが起き、ログが消える。保持期間を先に延ばす。

### 7.6 セキュリティ機器が試験を攻撃とみなす

WAF、Shield、API Gateway キー、 Cognito のレート、セキュリティグループ、NACL。事前に許可リストと、429/403 の見分けを決める。許可しすぎると本番耐性が分からないので、「WAF ありのラン」と「なしのラン」を分ける。

### 7.7 タイムアウトの入れ子

外側が先に切ると、内側はまだ仕事している。

典型（値は既定）:

| 層 | 既定の時間 | 切れたときの見え方 |
| --- | --- | --- |
| JMeter 応答タイムアウト | 設定次第 | クライアントエラー。サーバは成功していることがある |
| ブラウザ／呼び出し元 | アプリ次第 |  |
| API Gateway REST 統合 | 29 秒（Regional/private は引き上げ可、エッジは不可） | 504 |
| API Gateway HTTP API | 30 秒（引き上げ不可） | 504 |
| ALB idle timeout | 60 秒（1〜4000） | 504。access log の target_processing_time が idle と一致 |
| アプリ（Tomcat 等） | 設定次第 |  |
| RDS / Proxy | アイドル切断 | 次回 500 |
| 帳票 | ジョブタイムアウト | アプリが待ち続ける |

**帳票の同期呼び出しは、この入れ子のどこかで必ず死ぬ。** 29 秒の壁を超える帳票は、そもそも同期 API にしてはいけない。

ALB の keepalive はアプリ側を **ALB idle より長く** する。逆だと ALB が切れた接続に送って 502 になる（公式の注意）。

### 7.8 キャッシュを温めない／温めすぎ

- コールド: 初回だけ遅く、DB が本当のピークになる。本番朝一を見るなら意図的にコールドランを残す。
- ホットすぎ: 試験データが全部キャッシュに乗り、DB が暇。本番のヒット率と揃える。

### 7.9 隣接システムの破壊

メール、SMS、外部 PDF、電子契約、監視アラート。負荷で何千通も飛ばないようスタブか、専用サンドボックス。

### 7.10 合否を平均だけで出す

p99 が 8 秒でも平均 200 ms はよくある。ユーザの 1% が激怒する。

### 7.11 再現不能な一度きり

乱数シード、データ、タスク配置、ACU、キャッシュ状態が記録されていない。報告書に「再現手順」が無い試験は、改善検証ができない。

### 7.12 倫理と契約

許可のない負荷は攻撃である。クラウドは利用規約と、場合によって AWS への事前連絡（極端な帯域や特殊な試験）が要る。課金とデータ保護も試験計画に書く。

## 8. 打ち込み位置：全体試験でいちばん高いレバー

### 8.1 原則

```text
測りたいコンポーネントの「直前」から打つ。
前段を通すと、前段の試験になる。
```

例外は「ユーザ体感の E2E」だけである。E2E は別に 1 本取り、ボトルネック切り分け用のランと混ぜない。

### 8.2 推奨ラン構成

| ラン名 | 打ち込み | 目的 |
| --- | --- | --- |
| A. 体験 E2E | インターネット →（WAF）→ API Gateway → ALB → ECS | ユーザ体感。合格の参考。原因特定には使わない |
| B. アプリ本体（標準） | **ALB（可能なら内部 ALB / プライベート IP）→ ECS** | アプリ＋直下依存の能力 |
| C. 1 タスク | ALB → タスク数 1（オートスケール停止） | 単位能力 |
| D. データ層 | アプリ経由だがキャッシュ有/無、Proxy 有/無 | 依存の寄与 |
| E. 帳票隔離 | 帳票 API だけ、または帳票サーバ直 | 印刷室の天井 |
| F. ゲートウェイ | API Gateway 通し | スロットル、認可、マッピング、29 秒 |

**標準の全体性能はラン B + C で決める。** A は「前段込みで何 ms 足るか」の差分用。F はゲートウェイチームの試験。

### 8.3 なぜ API Gateway を通すと危険か（概要）

詳細は次章。要点だけ:

- 既定でアカウント×リージョンあたり **10,000 RPS**、バーストはトークンバケツ **最大 5,000**（一部リージョンは 2,500 / 1,250）。
- 429 がアプリエラーに見える。
- 統合タイムアウト 29/30 秒で帳票が 504。
- リクエスト課金が試験費用を支配する。
- 認可 Lambda が別ボトルネックになる。
- IntegrationLatency と Latency の差がゲートウェイ自身の仕事。

厨房を測りたいのに校門の回転木戸で人数を間引いている状態、がこれに当たる。

### 8.4 ネットワーク的な置き場所

- JMeter をパブリックインターネットに置くと、NAT・ISP・CloudFront が乗る。
- VPC 内に Fargate/EC2 でジェネレータを置くと、ALB 内部向けに打てる。
- 本番ユーザはインターネットから来るので、**両方の差**を一度測っておく（往復 10〜50 ms はよくある）。
- ジェネレータとターゲットを同じホストに置かない（自分の CPU を奪い合う）。

## 9. Amazon API Gateway

### 9.1 たとえ

校門の警備員。学生証を確認し、1 秒に通してよい人数を数え、中の建物へ案内する。警備員が遅いと、中の給食が速くても外では「学校が遅い」になる。

### 9.2 なぜ生まれたか

2010 年代、モバイルとマイクロサービスで「API を安全に外へ出す」仕事が急増した。認証、キー、レート制限、SDK 生成、キャッシュ、WAF 連携を、各チームが Nginx で自作していた。AWS は 2015 年に API Gateway を出し、これをマネージドにした。

その結果、**アプリの前に「共有の門」が常駐する**構成が標準になった。門には門の上限がある。

### 9.3 動作原理

クライアントの HTTPS を受け、ステージ・ルートを決め、オーソライザを呼び、統合（Lambda、HTTP、VPC Link→ALB/NLB）へ渡し、応答をマッピングして返す。

時計が二つある。

- **Latency:** クライアントから見た全体
- **IntegrationLatency:** 後ろの ALB/Lambda に渡してから返るまで

差が大きいなら、ゲートウェイ自身（認可、マッピング、ペイロード変換、オーソライザ）が重い。

スロットルはトークンバケツ:

- バケツにトークンが最大 **burst** 個（既定の説明では最大 5,000）
- 毎秒 **rate** 個補充（既定 10,000 RPS。アカウント×リージョンの全 API 合計）
- トークンが無いリクエストは **429 Too Many Requests**

Usage Plan / API キー、ステージスロットル、WAF がさらに下のバケツになる。どれか一つでも空なら 429。

REST API の統合タイムアウトは既定 29 秒。Regional / private はクォータ申請で延長できる場合がある。エッジ最適化は 29 秒のまま。HTTP API は 30 秒で上げられない。

VPC Link でプライベート ALB に直接つなげるようになった（従来 REST は NLB 経由が定番）。ホップが減るとレイテンシは良くなるが、**門の RPS 上限は残る**。

### 9.4 性能試験の観点

1. **アプリ能力の測定では、原則 API Gateway を外す。** ALB に直接（内部なら VPC 内から）打つ。
2. ゲートウェイ試験は別ラン。目標は「認可込みで 429 が出ないか」「IntegrationLatency と Latency の差」「マッピングの CPU 相当（大きな VTL）」。
3. アカウント上限は **全 API 共有**。隣のシステムの試験と同時に打つと、自分のアプリが悪くなくても 429。
4. バースト 5,000 は「一瞬の同時打ち上げ」に弱い。Synchronizing Timer での一斉発射はゲートウェイ試験になってしまう。
5. オーソライザの結果キャッシュ。キャッシュ無しだと Cognito/Lambda が先に死ぬ。
6. ペイロード 10 MB 上限。帳票 PDF を Gateway 経由で返す設計は、サイズと時間の両方で詰まりやすい。
7. 試験用 Usage Plan を本番キーから分離する。さもないと本番メトリクスと課金が混ざる。
8. 504 は「アプリが 29 秒超」であり、アプリ内部では成功していることがある。

### 9.5 見るメトリクス

- `AWS/ApiGateway` Count、4XXError、5XXError、Latency、IntegrationLatency
- 429 の有無（アクセスログの status）
- オーソライザ Latency
- キャッシュ Hit/Miss（REST キャッシュ利用時）

### 9.6 よくある間違い

- 「10,000 ユーザ」と「10,000 RPS」を混同する。
- エッジとリージョナルでレイテンシ差をアプリ差だと思う。
- ゲートウェイキャッシュが効いた状態だけを全体性能と呼ぶ。

## 10. Application Load Balancer（ALB）

### 10.1 たとえ

給食の配膳口。空いている窓に人を案内する。窓の奥が調理員（ECS タスク）。配膳口自体は薄いが、閉じた窓に料理を渡そうとすると事故る（502）。

### 10.2 なぜ生まれたか

古典的な ELB（Classic）は L4/L7 が混在し、コンテナやパスベースルーティングに弱かった。2016 年、ALB が HTTP 特化で登場し、ホスト/パス、マイクロサービス、ECS/EKS、認証、WAF と連携した。コンテナ時代の「サービスの玄関」になった。

Classic ELB は急激な負荷に事前ウォーム（AWS サポートへ連絡）が必要だった。ALB はより自動でスケールするが、**ゼロから数万 RPS を数秒で**出す試験では、スケールが追いつかず 503 が出ることがある。だからランプが要る。

### 10.3 動作原理

- L7。HTTP/HTTPS を終端し、ターゲットグループへ。
- ヘルスチェックに落ちたタスクには振らない。
- 接続はクライアント側とターゲット側で別。両方に idle timeout（既定 60 秒）。
- 2024 年以降、HTTP client keepalive duration（既定 3600 秒）で、クライアント接続の最大寿命も管理する。
- `TargetResponseTime` はアクセスログの `target_processing_time` と同じ。ALB がタスクに渡してから応答が戻るまで。**アプリ遅延の最もきれいな外測。**

アクセスログの三段時計:

- `request_processing_time` … 受けてからタスクへ渡すまで（ALB 自身、通常小さい）
- `target_processing_time` … タスクの仕事
- `response_processing_time` … クライアントへ書き戻す

クライアントの JMeter Elapsed がこの合計 + インターネット往復。差が大きければ経路か TLS。

### 10.4 性能試験の観点

1. **アプリ全体試験の標準エントリは ALB。** 可能なら internal ALB。
2. オートスケールを見る試験と、固定タスク数の試験を分ける。
3. ヘルスチェックが重いと、負荷でタスクが Unhealthy になり、残ったタスクに雪崩（カスケード）。
4. スロースタート（新規ターゲットに徐々に振る）がある場合、スケールアウト直後の p99 が悪化する。
5. sticky session は特定タスクに偏らせ、平均 CPU は低いのに p99 が悪い、を作る。
6. アイドル 60 秒と帳票同期は相性が悪い。
7. ジェネレータの Keep-Alive を有効にし、アプリの keep-alive を ALB idle より長くする。
8. HTTP/2 と HTTP/1.1 でコネクション数が全く違う。本番プロトコルに合わせる。

### 10.5 見るメトリクス

- RequestCount、TargetResponseTime（p95/p99）
- HTTPCode_Target_2XX/4XX/5XX
- HTTPCode_ELB_502/503/504
- UnHealthyHostCount、HealthyHostCount
- ActiveConnectionCount、NewConnectionCount、RejectedConnectionCount
- ConsumedLCUs（課金とスケールの目安）
- RequestCountPerTarget（1 タスクあたり。ECS サイジングの核）

### 10.6 502/503/504 の見分け

| コード | よくある意味 |
| --- | --- |
| 502 | タスクが接続を乱暴に切った。keep-alive 不整合、プロセス死亡 |
| 503 | ALB 自身のキャパ不足、または健全ターゲットゼロ |
| 504 | タスクが idle timeout まで返さなかった |

504 のとき target_processing_time ≒ idle timeout なら、アプリが時間内に終わっていない。

## 11. Amazon ECS（タスク単位で取る）

### 11.1 たとえ

調理員ひとりが「タスク」。厨房全体の平均「今日は一人あたり普通」でも、奥の一人だけ炎上していることがある。平均だけ見ると、火事が見えない。

だから **一人が何皿作れるか** を先に測り、人数を掛ける。掛け算が成り立たないとき、倉庫（DB）や印刷室が共有ボトルネックである。

### 11.2 なぜ生まれたか

EC2 に直接アプリを置くと、OS のパッチ、余った CPU、デプロイの食い違いがチームを縛った。Docker が「アプリと依存を箱に入れる」方法を広め、2014 年に ECS が箱の置き方をマネージドにした。2017 年の Fargate は「箱だけ頼めば、下のサーバを見なくてよい」ようにした。

課金と制限の単位が **タスクサイズ（vCPU とメモリの組）** になった。性能の単位も自然とタスクになる。サービス平均 CPU は「その組を何個並べているか」を隠す。

### 11.3 動作原理

- **タスク定義:** CPU 単位（1024 = 1 vCPU）とメモリ。Fargate は選べる組が固定。
- **サービス:** 望むタスク数を維持し、ALB に登録する。
- **CPUUtilization（サービス）:** 予約した CPU に対する使用率の平均。Linux ではソフト制限のため 100% を超えて見えることがある（余った CPU を借りる）。Fargate はタスクサイズがハードに近い天井。
- 1 タスク内に複数コンテナ（アプリ + sidecar）。メトリクスはタスクとコンテナで別。
- オートスケールは DesiredCount を変える。指標は CPU、メモリ、ALB RequestCountPerTarget、独自メトリクス。
- 2024-12-02: Container Insights の enhanced observability。タスク/コンテナまで自動で細かく取れる。
- 2026-06: 20 秒解像度メトリクスでスケールアウトが大幅に速くなった、という公式発表（ベンチでスケール開始まで約 76% 短縮、など）。それでも「秒で何倍」のスパイクには間に合わないことがある。

**接続プールはタスクの中にある。** タスクが 10 個、各プール最大 20 なら、Proxy/DB には最大 200 本。1 タスク試験で「20 本で足りた」を 10 倍すると、DB の `max_connections` を超える。

### 11.4 なぜタスク単位が必須か

1. **サイジングの単位だから。** 「何 TPS 欲しい / 1 タスクの TPS」がタスク数。
2. **平均が偏りを隠す。** sticky、長い帳票、特定シャード、GC 中のタスク。
3. **垂直と水平を分けられる。** 0.5 vCPU と 2 vCPU では、単一スレッドの帳票レンダが全く違う。
4. **オートスケール検証。** 閾値 70% が、1 タスク 70% なのか平均 70% なのかで動作が変わる。
5. **障害の単位。** 1 タスク死亡時のエラー率 = 1/N。N を決める根拠が 1 タスク能力。

### 11.5 試験の手順（推奨）

1. **オートスケールを止める。** Desired = 1。
2. ランプしながら TPS を上げ、p95 と CPU とエラーを見る。
3. 飽和点を記録する（TPS が増えず p95 が立ち上がる点）。
4. そのときの CPU、メモリ、DB 接続、キャッシュ、帳票を記録。
5. Desired = 2, 4, 8 で同じ負荷密度（RequestCountPerTarget が同じ）を再現し、直線性を見る。
6. 直線でないなら、共有依存が天井。
7. 最後にオートスケールを戻し、ピーク到達までの時間とオーバーシュートを見る。

**小学生向け:** まず選手一人のタイムを測る。次に 4 人でリレーできるか見る。4 人なのに一人分しか速くならないなら、バトン（DB）が問題。

### 11.6 見るメトリクス

- サービス: CPUUtilization、MemoryUtilization、RunningTaskCount、DesiredTaskCount
- ALB: RequestCountPerTarget、TargetResponseTime per ターゲット（ログ）
- Container Insights enhanced: タスク CPU/メモリ、ネットワーク、ストレージ
- アプリ: JVM ヒープ、GC、スレッドプール、Web サーバワーカー、コネクションプール active/idle/wait
- デプロイ中の minHealthyPercent、サーキット

Logs Insights 例（タスク単位）:

```text
fields @timestamp, TaskId, CpuUtilized, MemoryUtilized, CpuReserved
| filter Type = "Task"
| stats avg(CpuUtilized), max(CpuUtilized), avg(MemoryUtilized), max(MemoryUtilized) by TaskId
```

カスタムメトリクス化はカーディナリティ課金に注意。普段は Logs Insights、試験中だけメトリクス化する運用が安全。

### 11.7 よくある間違い

- サービス CPU 40% だから余裕、と判断する（実は 2 タスク中 1 つが 80%、もう 1 つが 0%）。
- 1 タスク飽和を取らず、いきなり 50 タスクで「目標 TPS 出た」と書く。夜間に 2 タスクまで縮んだ朝のスパイクで死ぬ。
- CPU だけ見てメモリリークを逃す。
- Fargate の ephemeral storage を埋め、帳票一時ファイルで 5xx。
- 起動時間を無視してスパイク試験を不合格にする（別指標にすべき）。

## 12. Amazon Aurora Serverless v2

### 12.1 たとえ

伸縮する倉庫。荷物が増えると床が広がり、減ると狭くなる。狭くしている最中にどっと荷物が来ると、広げる時間だけ作業が止まる。床をゼロまで畳む（オートポーズ）と、最初の荷物で起こす時間（十数秒程度、条件による）がかかる。

### 12.2 なぜ生まれたか

RDS/Aurora のプロビジョン型は、ピークに合わせて大きいインスタンスを常時借り、夜間は金が余る。逆に小さくするとセールで死ぬ。2018 年の Aurora Serverless v1 は「丸ごと別インスタンスに載せ替える」スケールで、接続が切れたり、段階が荒かった。v2（一般提供 2022 年頃）は **同じインスタンスの中で ACU を細かく変える** 方式になり、本番のオンラインに載るようになった。

その後、最低 0 ACU のオートポーズ、最大 256 ACU、スケール速度の改善（2026 年時点で「1 秒で +12 ACU」などの公式発表）が入った。速くなっても **ゼロ遅延ではない。** 性能試験では「伸びている最中の p95」を別指標にする。

### 12.3 動作原理

- **ACU（Aurora Capacity Unit）:** およそメモリ 2 GiB + 対応する CPU とネットワーク。
- スケール刻みは 0.5 ACU から。大きいほど一段が太い。
- Writer と Reader で独立に伸び縮み（クラスタ設定による）。
- ストレージは Aurora 共有ストレージ。計算（ACU）とディスクは別メーター。
- バッファプール（よく使うデータのメモリ）は ACU に比例する。最低 ACU が小さいと、暇な時間にメモリが捨てられ、次の負荷でディスク読み（キャッシュミス）になる。
- オートポーズ（min=0）は開発向き。本番の全体性能試験中は **ポーズさせない。min をワークセットが載る値以上にする。**
- スケール中もクエリは止めない設計だが、CPU/メモリの再配置で一時的に遅延が乗ることはある。
- アイドル接続が多いとスケールダウンしにくい、またはメモリが空きにくい、という運用上の話がある。RDS Proxy の整理とセットで見る。

### 12.4 性能試験の観点

1. **本測定の前に ACU を温める。** 試験用に min=max で固定するランを必ず 1 本取る（プロビジョン相当）。これがアプリ＋スキーマの真の能力。
2. その後 min〜max を本番設定に戻し、同じ負荷で「伸縮のペナルティ」を測る。
3. スパイク試験は ACU 追従遅延の試験であり、アプリ試験ではない。混ぜて不合格にしない。
4. 最低 ACU が低すぎると、バッファが乗らず毎回ディスク。p95 が安定しない。
5. 最大 ACU に張り付いたら、サーバレスではなく上限不足。
6. リーダーを使うなら、読込負荷をリーダーへ。ライターに分析クエリを混ぜない。
7. 性能 Insights を使うなら最低 ACU の推奨がある（公式は Performance Insights で 2 ACU など。時期で変わるので現行ドキュメントを確認）。
8. オートポーズ復帰を全体 SLA に含めない。含めるなら別要件。

### 12.5 見るメトリクス

- `ServerlessDatabaseCapacity`（ACU の実体）
- `ACUUtilization`
- `CPUUtilization`
- `FreeableMemory`
- `BufferCacheHitRatio`
- `DatabaseConnections`
- `CommitLatency`、`DMLThroughput`、`SelectLatency`
- `Deadlocks`、`BlockedTransactions`
- Read IOPS / Write IOPS（ストレージ側）
- 必要なら Performance Insights の待機イベント（CPU、I/O、Lock、LWLock）

**相関の見方:** JMeter の p95 が階段状に悪くなり、少し遅れて ACU が上がり、また良くなる、は「スケール待ち」。アプリのループバグではない。

### 12.6 よくある間違い

- コールド（min 0.5、バッファ空）の朝一数字を SLA にする。
- 接続を張りっぱなしでスケールダウンしないのを「バグ」と呼ぶ。
- v1 の「ポーズから復帰が数十秒〜分」と v2 を混同する。
- 最大 256 ACU あれば無限、と思う。単一ライターの直列ロックは ACU を増やしても解けない。

## 13. Amazon RDS Proxy

### 13.1 たとえ

倉庫の前の整理券機。中の席（DB の max_connections）は 200 しかない。外には 5,000 人が並ぶ。整理券機は「中で席を使っていない人の席を、次の人に使い回す」。

ただし、ある人が「自分専用のロッカー」（セッション状態）を使い出すと、その席は使い回せない。これが **ピン留め（pinning）**。整理券機がただの延長コードになり、料金だけ高い。

### 13.2 なぜ生まれたか

サーバレスとコンテナは **タスクや Lambda が急に増える。** それぞれが DB に接続すると、PostgreSQL/MySQL のプロセス/メモリが先に死ぬ。接続の確立自体も重い（認証、TLS、セッション初期化）。

2019 年頃に RDS Proxy が一般化し、「アプリと DB の間で接続をプールし、トランザクション単位で使い回す（multiplexing）」役になった。フェイルオーバー時にアプリから見た切断を短くする、という目的もある。

### 13.3 動作原理

```text
アプリ接続（多い、軽い、切ってもいい）
    ↓
RDS Proxy プール
    ↓ トランザクションが終わったら別アプリに貸し直す
DB 接続（少ない、重い、大事）
```

使い回しできないとピン留め。公式が挙げる例（エンジンで差がある）:

- `SET` でセッション変数を変える
- 一時表、一時シーケンス
- 大きな SQL 文（**16 KB 超**は全エンジンでピン留め、という公式条件）
- 一部のプレペアドステートメントやセッション状態
- `DISCARD ALL` 系のリセット
- PostgreSQL では変数設定がピン留めになりやすい

ORM（例: 巨大な IN 句を展開する Prisma 等）は 16 KB を簡単に超える。現場ではピン留めで多重化が死に、Proxy を外した事例もある。

クライアント接続の最大寿命は 24 時間（変更不可）。アイドルも Proxy が切る。アプリプールの idle timeout はそれより短くする。

余分なホップなので、健全時でもミリ秒単位の加算がある。効果は「接続嵐を防ぐ」側に出る。接続が少ない安定 ECS では、メリットよりピン留めとホップが目立つことがある。

### 13.4 性能試験の観点

1. **Proxy あり/なしを同じ負荷で 1 本ずつ。** 差がレイテンシ増だけなら、接続嵐が無い構成では外す判断材料。
2. 必須メトリクス: `DatabaseConnectionsCurrentlySessionPinned`。貸出中の大半がピン留めなら、Proxy はプールではない。
3. 1 タスクのプールサイズ × 最大タスク数が、Proxy の MaxConnectionsPercent と DB `max_connections` に収まるか。
4. フェイルオーバー試験は別ラン。通常負荷の p95 と混ぜない。
5. Lambda のように接続が短命な構成では Proxy の価値が高い。ECS 常駐では再評価する。
6. 初期化クエリに共通 `SET` を寄せ、ピン留めを減らす。
7. 16 KB 超 SQL を試験データで再現する（本番の巨大 IN 句）。小さな SQL だけの試験は楽観的すぎる。
8. TLS 終端と認証（Secrets Manager）の遅延を Connect Time で見る。

### 13.5 見るメトリクス

- ClientConnections
- DatabaseConnections
- MaxDatabaseConnectionsAllowed
- DatabaseConnectionsCurrentlyBorrowed
- DatabaseConnectionsCurrentlySessionPinned
- DatabaseConnectionsCurrentlyInTransaction
- QueryDatabaseResponseLatency（ある場合）
- ピン留め率 = Pinned / DatabaseConnections（理想は低い。ゼロでなくても、大半がピンなら失敗）

公式ダッシュボードは「ピーク見込みの 30% ヘッドルーム」を推奨している。試験で 100% まで埋めると、本番のゆらぎで拒否が始まる。

### 13.6 よくある間違い

- アプリ側プール + Proxy プール + DB の三重プールで、ピン留めされたままアプリが接続を握る。
- Proxy を入れれば `max_connections` を無視できる、と思う。ピン留め時は 1:1。
- ヘルスチェックの `SELECT 1` がアイドル判定を壊し、接続が減らない。

## 14. Amazon ElastiCache（Valkey / Redis OSS / Memcached）

### 14.1 たとえ

厨房の手元棚。毎日出すソースは棚、珍しい香辛料は倉庫（DB）。棚が空だと、全員が倉庫に走る（キャッシュスタンプ）。棚の一瓶だけ人気（ホットキー）だと、その瓶の前だけ行列。

### 14.2 なぜ生まれたか

Web がスケールする過程で、同じ読込を DB に何度も投げて死ぬ、が典型パターンになった。memcached（2003 年頃）が「メモリにキーと値」を広め、Redis（2009 年）がデータ構造と永続を足した。AWS は 2011 年に ElastiCache を出し、運用（パッチ、フェイルオーバー、バックアップ）を肩代わりした。2024 年以降は Valkey（Redis のフォーク）も選択肢。Serverless も出た。

アプリ開発者は「キャッシュすれば速い」と書く。性能試験では **当たったときと外れたときで、システム全体の形が変わる** ことを測る。

### 14.3 動作原理

- メモリ上のキーバリュー。ネットワーク 1 往復はサブミリ〜数ミリ秒。TLS と新規接続はその何倍も高い。
- Redis/Valkey のコマンド処理は歴史的に単一スレッドが中心。**EngineCPUUtilization** が本体の忙しさ。ノード CPU 全体（CPUUtilization）とは別。IO スレッドや Enhanced I/O でネットワークは並列化されている世代がある。
- Cluster mode disabled: 一つのキー空間。マルチキーが楽。メモリ天井は 1 ノード。
- Cluster mode enabled: 16384 スロットに分割。クライアントは全シャードに接続。マルチキーはハッシュタグ無しだと失敗。
- Eviction: メモリ満杯でキーを捨てる。捨てた直後は DB へ。
- TTL: 同じ時刻に大量期限切れ → 一斉ミス（thundering herd）。
- 接続: ノードあたり `maxclients` 既定 65,000 だが、実効はメモリと TLS で下がる。タスク数 × プールがこれを超える。

### 14.4 性能試験の観点

1. **ウォームランとコールドランを分ける。** コールドは DB 試験に近い。
2. 本番のヒット率（例: 90%）を目標にデータと TTL を組む。100% ヒットはキャッシュ単体試験。
3. ホットキーを意図的に入れる（同じ商品 ID の嵐）。Cluster でも一人のプライマリに寄る。
4. 接続はプール必須。毎リクエスト接続は TLS でアプリ CPU が死ぬ。JMeter が直接 Redis を叩くなら、本番アプリのプール挙動とは別物。
5. Cluster クライアントの MOVED/ASK。非対応クライアントは試験に使わない。
6. 書込負荷（セッション保存、ロック）は EngineCPU とレプリケーション遅延を見る。
7. フェイルオーバー中のエラーと、アプリのリトライ嵐。
8. キャッシュを「ない」とみなしたフォールバックが DB を殺すか（stampede 対策: ロック、stale、シングルフライト）。

### 14.5 見るメトリクス

- CacheHitRate、CacheHits、CacheMisses
- EngineCPUUtilization（Redis/Valkey で特に重要。70〜90% で警戒）
- CPUUtilization
- Evictions、Reclaimed
- CurrConnections、NewConnections
- ReplicationLag
- NetworkBytesIn/Out、NetworkBandwidth 制限
- ホットキーがあれば ENGINE の slowlog、または独自メトリクス
- アプリ側: キャッシュ待ち時間、フォールバック回数

### 14.6 よくある間違い

- ヒット率だけ見て EngineCPU を見ない（単一キーの GET 嵐）。
- 試験前にキーを全投入し、本番よりずっとホット。
- TTL を試験短縮のために 10 秒にし、本番 1 時間と違うミスパターンにする。
- キャッシュ障害時の挙動を一度も落とさずに「冗長」と書く。

## 15. 帳票サーバ（SVF / JasperReports など）

### 15.1 たとえ

成績表を一枚ずつ丁寧に印刷する部屋。調理（JSON API）は 0.2 秒、印刷は 8 秒。印刷室のプリンタは 8 台しかない。9 人目は前の人が終わるまで待つ。待っている間、API の糸（スレッド）も席も塞がる。門（API Gateway）は 29 秒で追い出す。

### 15.2 なぜ「脇役」が全体を支配するか

日本の業務システムでは、見積・請求・納品・帳票 PDF がオンラインの直後に要求されることが多い。歴史的に SVF（ウイングアーク）や JasperReports、Crystal、自前 PDF が「同期 HTTP で生成して返す」形でアプリに埋め込まれた。

マイクロサービス化しても、「登録 API の最後に帳票サーバへ HTTP」が残りやすい。すると:

- 帳票の CPU（レイアウト、フォント、画像、ページ数）が ECS タスクではなく **別 JVM** を食う。
- 同時実行数に製品上限がある（SVF 系ならジョブ並列、プリンタスレッド数など）。
- 一時ディレクトリにファイルが溜まると経年劣化（公式 KB にもある）。
- DB を帳票側が再検索し、オンラインと同じ倉庫を二重に叩く。

Jasper の経験則では、同時実行はメモリ（仮想化／ページのディスク退避）が先に限界、という話が多い。SVF は並列ジョブ設定とクエリ設計が支配的。どちらも **OLTP の TPS 試験に帳票を混ぜると、先に印刷室が満杯** になる。

### 15.3 動作原理（同期呼び出し）

```text
ユーザ → API Gateway → ALB → ECS
                         → 帳票サーバへ HTTP/RPC
                         → 帳票サーバが DB を読む（または ECS が渡したデータで描画）
                         → PDF バイトが戻る
                         → ECS が応答
```

時計:

- JMeter Elapsed ≒ アプリ + 帳票 + DB
- 帳票内部: データ取得、レイアウト、フォント、圧縮、書き出し
- 並列上限を超えると **キュー待ち** が Elapsed に上乗せ。アプリ CPU は闲しているのに遅い。

非同期化（ジョブ ID を返し、完成後に S3）すると、オンライン SLA から印刷時間を外せる。全体試験では「同期のまま測る」と「非同期後のオンラインだけ測る」を分ける。

### 15.4 性能試験の観点

1. **帳票を含むミックスと、含まないミックスを別ラン。** 含めないランが API 本体の能力。
2. 帳票だけを隔離（帳票サーバ直、または専用 API）。同時 N 本で p95 とエラー、JVM、キューを取る。これが印刷室の天井。
3. 代表帳票をサイズ別に（1 ページ、10 ページ、画像多め、明細 1,000 行）。平均的な 1 種だけでは足りない。
4. 同期なら、p99 が API Gateway 29 秒 / ALB idle / アプリタイムアウトに対しどれだけ余裕があるか。
5. ECS スレッドプールが帳票待ちで埋まり、帳票を呼ばない API まで遅くなる **スレッド飢餓** を見る。隔離するなら別サービス・別タスク・非同期。
6. 帳票の DB アクセスがオンラインと同じコネクションプールを奪わないか。
7. 一時ディスク、フォントキャッシュ、PDF のヒープ。ソークでディレクトリ件数を見る。
8. デバッグログ、トレース全ページ計算は本番オフ（SVF 公式も測定時 OFF を注意）。
9. 外部 SaaS 帳票はスタブ＋本番相当遅延。さもないと試験が SaaS のレート制限試験になる。

### 15.5 見るメトリクス

- 帳票ジョブ: 受付、実行中、キュー待ち時間、成功/失敗、ページ数
- JVM: ヒープ、GC 停止、スレッド、CPU
- ディスク: 一時ディレクトリ件数と inode
- ネットワーク: PDF サイズ × TPS が帯域を超えないか
- ECS: 帳票待ちスレッド数、タイムアウト件数
- ALB 504、API Gateway 504 の同時発生
- DB: 帳票クエリの待機イベント

### 15.6 よくある間違い

- 全体 TPS 目標に帳票 10% を混ぜ、帳票天井で不合格にし、ECS を増やす（印刷室は 1 つなので効かない）。
- 1 ページ PDF だけで「帳票問題なし」。
- 同期のまま Gateway 経由でバイナリ返却し、29 秒と 10 MB に当たる。
- 帳票サーバをシングルインスタンスのまま ECS だけオートスケール。

## 16. 段をまたいだ切り分け（動作イメージ）

遅さは「合計」でしか見えない。分解する。

```text
JMeter Elapsed
  = インターネット往復
  + API Gateway（Latency - IntegrationLatency）
  + 認可
  + ALB request_processing
  + TargetResponseTime（アプリ）
      = アプリ CPU
      + キャッシュ往復
      + Proxy 往復
      + DB
      + 帳票待ち
      + 外部 I/O
  + ALB response_processing
```

**手順:**

1. 同じ負荷を ALB 直打ちと Gateway 経由で 1 本ずつ。差が Gateway。
2. キャッシュをバイパス（Cache-Control または別キー）して差がキャッシュ。
3. 帳票 API をミックスから外して差が帳票。
4. 1 タスクにして CPU 100% 近傍ならアプリ CPU。CPU が低いのに TargetResponseTime が長いなら待ち（DB/帳票/外部）。
5. DB の待機が CPU なら ACU 不足、Lock ならクエリ/インデックス、IO ならバッファやストレージ。
6. Proxy のピン留め率が高いなら接続設計。
7. タスクを倍にして TPS が倍なら水平スケール可。倍にならなければ共有天井。

**小学生向け:** 遠足の遅れを、集合、バス、徒歩、昼食に分けて時計を置く。バスだけ遅いか、歩きが遅いかを見分けてから対策する。

## 17. 負荷モデルの作り方

### 17.1 同時ユーザと TPS の変換

```text
TPS ≒ 同時仮想ユーザ / 1 ユーザの平均サイクル秒
サイクル秒 = 思考時間合計 + 応答時間合計
```

応答時間が悪化すると、固定スレッドでは TPS が自然に落ちる（クローズド）。本番が「到着率一定」（オープン）なら、JMeter も Open Model か、十分なスレッド + ペーシングで近似する。さもないと、本番より優しい。

### 17.2 ランプの形

```text
0 ──ramp── 目標の 50% ──hold（ウォーム）── ramp ── 目標 100% ── 定常 20〜60 分 ── ramp down
```

スパイクは別:

```text
定常 20% ── 数秒で 200% ── 数分 ── 戻す
```

### 17.3 ミックス例（イメージ）

| 業務 | 比率 | SLA p95 | 備考 |
| --- | --- | --- | --- |
| 参照系 API | 70% | 300 ms | キャッシュ効く |
| 更新系 API | 20% | 500 ms | ロック注意 |
| ログイン | 5% | 400 ms | Cognito |
| 帳票 | 5% | 8 s | 別天井。同期なら比率を過大にしない |

比率はアクセスログの 95 パーセンタイル日ではなく、**ピーク 1 時間** から取る。

## 19. 合否判定の例

前提: 打ち込みは内部 ALB。タスク 8。min ACU はウォーム済み。帳票 5% 同期。ウォームアップ 10 分除外。定常 30 分。

| 項目 | 合格 | 条件付き | 不合格 |
| --- | --- | --- | --- |
| 主要参照 p95 | ≤ 300 ms | 300〜500 ms | > 500 ms |
| 更新 p95 | ≤ 500 ms | 500〜800 ms | > 800 ms |
| 帳票 p95 | ≤ 8 s | 8〜15 s | > 15 s または 504 |
| エラー率（真の失敗） | < 0.1% | 0.1〜1% | > 1% |
| 目標 TPS | 維持 | 5% 未満の欠落 | 維持不能 |
| タスク CPU 平均 | < 70% | 70〜85% | 85% 超が持続（余力なし） |
| タスク偏り | max-min < 20pt | 20〜40pt | 一部だけ 100% |
| Proxy ピン留め | 低位安定 | 中程度 | 貸出の大半 |
| ACU | 上限に余裕 | 時々接近 | 張り付き＋p95 悪化 |
| キャッシュヒット | 本番同等 | やや低い | コールドのまま |
| ジェネレータ CPU | < 70% | 70〜80% | > 80%（無効） |

条件付きはリリース可否を「リスク受容の署名」に回す。黙って合格にしない。

## 23. まとめ（これだけは外さない）

1. **測りたい段の直前から打つ。** API Gateway 通しはゲートウェイ試験になりやすい。アプリの全体性能は ALB から。
2. **ECS は 1 タスクの能力を先に取る。** 平均 CPU では偏りもサイジングも分からない。
3. **JMeter は非 GUI、生 JTL、HTML、サーバ側メトリクスの四点セット。** GUI と平均応答時間だけでは不足。
4. **サーバレスは伸縮中の遅さを、アプリの遅さと分けて記録する。** Aurora の ACU、ALB の 503、ECS の起動。
5. **RDS Proxy はピン留め率、ElastiCache はヒット率と EngineCPU、帳票は同時実行とキューを見る。** 見ないと「ECS を増やす」という間違った薬を出す。
6. **帳票同期は全体の天井になり、タイムアウトの入れ子（29 秒）に当たる。** 混ぜるなら比率と SLA を別に。
7. **合否は事前の数値。** 事後の感想で合格にしない。
8. **歴史が教えること:** 遅さはいつも「新しい共有層」に移る。門、配膳、調理員、棚、整理券、倉庫、印刷室。新しい層を足したら、その層の試験観点を足す。
